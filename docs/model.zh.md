# 惜流 ThriftFlow · 上下文成本模型

> 本文件是 `model.ts` 的数学说明书。**唯一权威是代码**：本文所有数字都能由
> `node selftest.ts --tables` / `node selftest.ts` 复算；散文与代码冲突时，代码对。

---

## 1 要回答的问题

dsh 的"思考时间长 + token 消耗多"不是一个量，而是两个互相拉扯的量：

- **时间** ≈ 输出 token（含 reasoning）的生成 + 上下文的 prefill
- **账单** ≈ prompt token × 步数，其中绝大部分是 cache read

把压缩率、时间、token 写进同一组方程后，可以得到三个可以直接执行的判据：
压缩阈值取多少、保留量能不能压、摘要要多短。

## 2 符号

| 符号 | 含义 | 单位 |
|---|---|---|
| `c_i` | 第 i 步命中缓存的 prompt token | token |
| `f_i` | 第 i 步未命中的 prompt token | token |
| `o_i` | 第 i 步输出（含 reasoning） | token |
| `L_i = c_i + f_i` | prompt 总长（模型可见上下文） | token |
| `θ` | 压缩触发阈值（**绝对值**，不是窗口比例） | token |
| `ρ` | 压缩后保留量 | token |
| `s` | 摘要输出长度 | token |
| `g` | 每步上下文增长 | token/step |
| `ō` | 每步平均输出 | token/step |
| `γ` | 降智惩罚系数（γ>1：返工/降智让每步变贵） | — |
| `W` | 模型上下文窗口 | token |

三档单价（**时间**，不是钱）：

| 常数 | 含义 | 实测值 |
|---|---|---|
| `τ₀` | 每次调用的固定开销 | 486 ms |
| `α_L` | 命中 prompt 每 token prefill | 5.950 µs |
| `α_M` | 未命中 prompt 每 token prefill | 20.992 µs（= 3.5×α_L） |
| `α_O` | 输出每 token 生成 | 4.032 ms |

## 3 状态方程

```
L_{i+1} = L_i + o_i + u_i + ε_i        u=工具结果，ε=插件注入
f_i ≈ ΔL_{i-1}                         fresh ≈ 上一步新增的表面
c_i ≈ L_{i-1} - f_i
```

压缩把 `L` 从 `θ` 砍回 `ρ`，形成锯齿：

```
压缩率   κ_r = ρ/θ
平均高度 L̄  = (ρ+θ)/2
周期步数 n_c = (θ-ρ)/g
```

## 4 两个代价泛函

```
T_i = τ₀ + α_L·c_i + α_M·f_i + α_O·o_i
C_i = π_cache·c_i + π_in·f_i + π_out·o_i
```

会话总量（`N` 步，约 `N·g/(θ-ρ)` 次压缩）：

```
T_tot = N·Φ
Tokens = N·L̄
```

## 5 推导：最优压缩带

### 5.1 压缩代价必须写成 θ 的函数

一次压缩的代价 = 摘要器读全量 surface + 重读保留区 + 读与生成摘要：

```
κ(θ) = α_M·θ + α_O·s              ← 注意 θ 在 κ 里面
```

**把 `κ` 当常数是错的**：它对 θ 求导不为零，会在求导时被吞掉一部分，得到偏大的阈值。
正确做法是先把 `κ(θ)` 代入，再求导。

### 5.2 目标函数

```
Φ(θ) = γ·[τ₀ + α_L·L̄ + (α_M-α_L)·ḡ + α_O·ō]
     + g·[α_M(θ+ρ+s) + α_O·s]/(θ-ρ)
```

第二项 = 一个压缩周期的一次性代价摊销到每步；一次性代价含
`α_M·(θ+ρ+s)`（读全量 + 重读保留区 + 读摘要）与 `α_O·s`（生成摘要）。

### 5.3 求导

```
d/dθ [γ·α_L·(ρ+θ)/2]                 = γ·α_L/2
d/dθ [g·(α_M(θ+ρ+s)+α_O·s)/(θ-ρ)]     = -g·[α_M(2ρ+s) + α_O·s]/(θ-ρ)²
```

第二步的代数关键：`α_M(θ+ρ+s)` 求导给出 `α_M(θ-ρ) - α_M(θ+ρ+s) = -α_M(2ρ+s)`，
即 `α_M·ρ` 出现两次。置零：

```
(θ-ρ)* = √( 2g·[α_M(2ρ+s) + α_O·s] / (γ·α_L) )
θ*     = ρ + (θ-ρ)*
```

二阶导 `2g(2α_Mρ+…) /(θ-ρ)³ > 0`，唯一极小值。

### 5.4 三条结构性结论

1. **θ 从右侧消失**：闭式解，不需要迭代。
2. **决定 θ\* 的是摘要的"生成"成本 `α_O·s`，不是被摘要的上下文有多大**——读入成本
   随 θ 线性增长，作为带内边际成本被求导吃掉了。所以**摘要越短，阈值可以越低**。
3. **band\* 里没有 `W`**：最优阈值与窗口大小无关。`0.8·W` 这种写法不是"调大了一点"，
   而是错误地缩放；1M 窗口下它等于 800k，等于几乎不压缩。

### 5.5 γ 的作用

γ 在**分母**：越容易降智，带越窄、阈值越低（更早、更频繁地压缩——用一次性代价买断
后续每一步的 γ 溢价）。

```
γ=1.0 → θ*=80.2k   4.31 s/步   3.87 h（3,233 步）
γ=1.3 → θ*=74.0k   5.56 s/步   4.99 h
γ=2.0 → θ*=65.5k   8.44 s/步   7.58 h
γ=3.0 → θ*=59.0k  12.53 s/步  11.25 h
```

（`ρ=30k, s=2000, g=800`，由 `--tables` 输出）

## 6 决策判据

### 6.1 保留量 ρ：**不要解它，当约束给**

```
∂Φ/∂ρ = γ·α_L/2 + γ'(ρ)·W + g·[α_M(2θ+s)+α_O·s]/(θ-ρ)² = 0
```

把它写成"γ 的余地"就是汇率（`ρ=30k, s=2000, γ=1, g=800`）：

| 把 ρ 压到 | 省下（3,233 步） | 要求 γ ≤ |
|---|---|---|
| 25k | 2 分 | 1.008 |
| 20k | 4 分 | 1.016 |
| 15k | 5 分 | 1.025 |
| 10k | 7 分 | 1.033 |
| 5k | 9 分 | 1.042 |

**汇率：砍 10k 保留量 ≈ 1.60% 的 γ，每步只省 0.066 s。**

结论：保留量的全部调整空间只值 9 分钟，赔付上限却是 γ=3 时的 +7 小时。
**收益与风险不对称 → ρ 不进优化器，只作约束。**

### 6.2 摘要长度 s：真正的第二旋钮

| s | θ\* | 单次压缩 | 每步 | 3,233 步 |
|---|---|---|---|---|
| 200 | 53.6k | 2.6 s | 4.156 | 3.73 h |
| 500 | 59.7k | 3.9 s | 4.193 | 3.77 h |
| 1,000 | 67.8k | 6.1 s | 4.241 | 3.81 h |
| 2,000 | 80.2k | 10.4 s | 4.314 | 3.87 h |
| 4,000 | 98.5k | 18.9 s | 4.424 | 3.97 h |
| 8,192 | 126.3k | 36.5 s | 4.589 | 4.12 h |

### 6.3 压缩是否值得做

```
值得压缩 ⟺ 剩余步数 × α_L·(θ-ρ)/2 > α_M·(θ+ρ+s) + α_O·s
```

即收益按剩余步数摊销、代价立刻支付。短会话（如 22 步）压缩是纯亏损——这解释了为什么
当前 800k 的默认值在短会话里"恰好没事"。

### 6.4 effort 的弹性规则

```
降 effort 值得 ⟺ |Δ ln T̄| > |Δ ln N|
```

每步省下的比例要大于步数增加的百分比。这条只能靠 A/B 观测，不能先验假定。

## 8 dsh 引擎侧必须处理的三个坑

1. **会话日志是 zstd 多帧拼接**（一次 flush 一帧；最长会话 **10,309 帧**）。
   Node 的 `zstdDecompressSync` **只解第一帧**，直接解会得到 1 行、看起来像空会话。
   必须先按 magic `28 B5 2F FD` 切帧，再逐帧解压（`replay.ts` 的 `decodeFrames`）。
2. **SQLite 索引默认关闭**：`dsh-base` 的 `session-query-sqlite` 是 `openAt: never`，
   搜索直接报 `SESSION_QUERY_SEARCH_DISABLED`，所以回放只能走文件。
3. **目录名被转义**（`--D-~4EE3~7801~5E93-ThriftFlow--`，CJK 转义不可逆）：当不透明 id 用，
   不要反解回路径。

另外两个观测事实（不是坑，但会影响判读）：

- **压缩发生在步内**：`tool/result → compaction/start → summary → end → request/header → assistant/message`。
  所以一次压缩的 surface 取**上一次模型调用**的 prompt，不能取压缩后那一步的 prompt
  （否则 surface 会算成 0 或压缩后的小值）。
- `compaction/prune` 事件带 `shadowedTokenCount`，可用于统计工具结果修剪量。

## 10 双通道设计

模型给出的两个旋钮分别落在两个不同时间尺度上，所以拆成两条通道：

```
通道 1（会话内，步尺度）：dsh compaction-basic
  θ = 绝对值（解出来的），ρ = 30k（约束），s = 尽量短
  收益：3,233 步 6.03h → 3.77h；prompt 1.55B → 0.15B
  风险：≈0，不依赖摘要器质量

通道 2（跨会话，天尺度）：Moonshadow（原文冷存 + T0-T9 分层 + 精确回取）
  作用：让被压掉的内容仍可寻址取回 → γ 保持在 1.0 附近
  收益：等价于 γ 从 1.3 降到 1.0（−1.12h / 3,233 步）
  待补：抽取器接通，把压缩率从 0.498x（膨胀）推到 <1
```

**为什么不让 Moonshadow 直接当会话压缩器**：它的 T0–T9 半衰期是"天/小时"尺度，
而会话内压缩是"步"尺度；且其现行压缩率 0.498x 会让 `s` 变大（`s` 从 2000 涨到 4000
会把 θ\* 从 80k 抬到 98.5k，单步 +0.11 s），净效应为零或负。

## 11 `model.ts` API

```ts
import {
  MEASURED, PROVENANCE,                 // 常数与证据等级
  optimalBand, optimalThreshold,        // band*(ρ,s,g,γ) / θ*
  perStep, sessionCost,                 // 每步 / 每会话成本（含 steady|transient）
  predictStepSeconds, predictCompactionSeconds,  // 逐步回放预测
  exchangeRate, breakEvenGamma, worthCompacting, // 三条判据
  recommend,                            // 建议配置（含理由）
  fit, rSquared,                        // OLS 标定
} from './model.ts';
```

`replay.ts`：`discoverSessions()` / `readLogFile()` / `readSession()` / `estimateGrowth()`，
外加审计 CLI：

```
node replay.ts test/fixtures/synthetic-long-session.jsonl   # 合成夹具（明文 jsonl）
node replay.ts <session.v3.jsonl.zstd>  # 真实会话（自动识别 zstd）
node replay.ts --limit=3                # 不带文件：审计最大的 N 个会话
```

报告口径：每一轮 = 一次模型调用，字段为 `promptTokens = cacheRead + input`、
`cacheReadTokens`、`completionTokens`、`durationMs`；判定用 **|总时间残差| < 10%**，
逐轮 MAPE/中位偏差只作离散度诊断（单轮噪声来自重试与工具时序）。
`selftest.ts`：CLI（`--tables` / `--policy` / `--flash-only` / `--limit=N`）。

`prescribe.ts`：处方 CLI，**不含任何新数学**，只调用 `recommend()` / `sessionCost()`：

```
node prescribe.ts test/fixtures/synthetic-long-session.jsonl   # Diff 表 + 预计节省 + 可直接粘贴的 patch
node prescribe.ts --limit=1        # 对最大的真实会话开处方
```

两个配置项的推导：

- `thresholdRatio = θ* / W`：θ\* 是绝对值，所以比例只是把它换算成 dsh 的配置单位。
- `maxInlineBytes`：用 `n_c/2`（一个结果在压缩周期里的期望剩余寿命）算持有成本
  `α_M + α_L·n_c/2`（s/token），与"从 spill 重取一次"的代价 `τ0 + t_tool` 相除得到
  break-even，再取 `min(8,000, break-even)`：8,000 是早前对真实日志的建议值
  （41 个结果里 8 个超过 8,192 字符，最大 54,045 字符），break-even 保证它不会裁掉
  "其实更便宜地留在上下文里"的部分。同时把 `tool-result-pruner.thresholdChars`
  对齐到同一预算，避免"先落盘再剪枝"两道工序。

## 12 已知局限

1. **政策级预测 MAPE 13.7%**（未达 10%）：`steady`/`transient` 判据用 `steps×g ≤ θ-ρ`，
   但部分会话起始上下文已经很大、或压缩成簇发生，导致判据与实际锯齿不一致。
   改进方向：用观测到的 `L̄` 与压缩次数反解 `g`，或让 `sessionCost` 接受初始上下文。
2. **`s` 与 `α_M·θ` 未独立标定**：`compaction/summary` 不带 usage；压缩项预测 +17.5%
   主要来自这里（CJK 用 chars/4 会低估，摘要器的系统前缀可能部分命中缓存）。
3. **常数只对 `deepseek-flash` 家族成立**：唯一 `deepseek-v4-pro` 会话残差 −53.1%，
   说明 `α_O` 与 `τ₀` 是模型相关的，换模型必须重拟合。
4. **未建模的项**：工具执行时间（另占约 20% 墙钟）、`compaction/prune` 的修剪收益、
   `retry` 造成的重复调用。
5. **`steady` 假设均匀锯齿**：真实日志里 `L` 的分布（中位 434k、p90 703k）与之大致相符，
   但压缩簇、手动 `/compact` 会破坏它。
