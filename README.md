# ThriftFlow（惜流）

**Agent 运行时的上下文成本治理平面。** 拿你自己的会话日志，算出钱和时间花在哪，再算出一个更好的阈值写回去。

`thresholdRatio: 0.8` 这个默认值，在 1M 窗口下等于「几乎不压缩」：上下文涨到 800k 才动手，而此前的每一步都要把接近窗口上限的上下文过一遍（即便 99.7% 命中缓存，也只是单价便宜，量一分没少）。

| 产出 | **8 个文件**（7 个 TS：接口 / 状态机 / 参与者 / 协调者 / 本地消息表 / 内存实现 / 压测脚本，+ 1 份设计说明） | ✅ 已入库 `tcc-inventory/` |
| 自动断言 | **39 项通过 / 0 失败** | ✅ 可复现：`node tcc-inventory/simulate.ts` |
| 累计 token | 624K | 宿主面板 · n=1 |
| 缓存命中率 | **99%** | 宿主面板 · n=1 |
| 墙钟耗时 | 4 分 51 秒 | 宿主面板 · n=1 |
| 费用 | **¥0.51** | 宿主面板 · n=1 |

**结论**：`maxInlineBytes: 8000` 把 Tool Schema 完整保住了，全程没有截断崩溃；compaction 在长思考场景下没有丢推理上下文——39 项断言里包含「60 并发抢 20 件库存」「Confirm 已执行但响应丢失」「进程被杀后从快照恢复」这类**只有连贯上下文才写得对**的场景，全部通过，没有逻辑断片。

> ⚠️ **口径声明（别混着引用）**：断言数、产物文件数、`simulate.ts` 可复现性属于**已核验事实**；token / 缓存命中 / 耗时 / 成本四项来自宿主前端面板，**n=1、不可复现**，它们只证明「这一次没被压缩压断」，**不构成任何收益结论、也不能当业绩**。

> 复核方式：`cd tcc-inventory && node simulate.ts`（零依赖，Node ≥ 22.18 直接跑 `.ts`）。

## 🚨 两个反直觉的结论

推导基于真实会话日志（3,233 步、平均上下文 423k、峰值 793k、实测 5.69 h）。**每一条都能用你的日志复算。**

1. **最优压缩阈值与窗口大小无关。**
   `band*` 的闭式解里没有 `W`：
   `(θ-ρ)* = √( 2g·[α_M(2ρ+s) + α_O·s] / (γ·α_L) )`
   它取决于增长速率 `g` 与摘要成本 `α_O·s` 的博弈，而不是窗口有多大。`0.8·W` 不是「调大了一点」，是**错误地缩放**。
2. **决定阈值的是摘要「生成」成本，不是被摘要的上下文大小。**
   读入成本随 θ 线性增长，作为带内边际成本被求导吃掉了。所以**摘要越短，阈值可以越低**——压阈值要先压摘要长度。

## ⚡ 核心机制

- **`model.ts`**：拟合自真实日志的时间方程（**R² = 0.764**，内置常数）
  `ms = 486 + 5.950·cached_tok(µs) + 20.992·fresh_tok(µs) + 4.0321·output_tok(ms)`
  同一会话的 3,229 个干净步骤重标定得 R² = 0.818，但常数会漂（τ0 248 ms vs 486 ms）——所以下面报成绩时一律标明用的是哪组常数。纯函数，无 I/O。
- **`audit`**：黑匣子审计。输入日志，输出时间分解、缓存命中、压缩判定、逐轮残差。
- **`prescribe`**：输出最优配置 Diff + `[ESTIMATED]` 投影 + 可直接粘贴的 patch。
- **`compare`**：同一份日志的策略 A / 策略 B 受控投影；`--after-apply` 只做**带护栏**的实测（配置不在位就拒绝报数）。
- **`apply`**：一键写入宿主配置（备份 / 校验 / `--restore` 回滚）。

### ①b 异常波动说明 —— 残差为什么不是 0

**本机 375 个可计分会话里，191 个 |总时间残差| ≥ 10%。** 全都通过的模型才该被怀疑。

先看默认 `audit`（本机观测时长最长的 3 份，2.0–5.7 h）：

| 会话 | calls | 实测 | 残差 | 判定 |
|---|---|---|---|---|
| `3a891a92` | 3,233 | 5.72 h | **−0.0%** | 通过 |
| `d448976a` | 2,034 | 3.60 h | **+3.7%** | 通过 |
| `5cc37e78` | 1,368 | 2.00 h | **+3.1%** | 通过 |

再看三份**不通过**的短会话（都在本仓库自己的会话目录下，`audit <path>` 可复现）：

| 会话 | calls | 实测 | 残差 | 残差差额 | 被点名的异常行 | 占差额 | 剔除后残差 |
|---|---|---|---|---|---|---|---|
| `98dc66` | 45 | 504.65 s | **−14.9%** | −75.0 s | 第 5 轮 `completion=30,905 tok`：实测 156.6 s / 预测 125.2 s | **41.9%** | −12.5% |
| `71458c` | 277 | 1,350.23 s | **−12.9%** | −174.8 s | 第 275 轮 `prompt=0`：实测 4.5 s / 预测 0.49 s | **2.3%** | −12.7% |
| `56550a` | 8 | 170.33 s | −9.3% | −15.9 s | 第 6 轮 `prompt=0`：实测 5.9 s / 预测 0.49 s | **33.9%** | −6.4% |

三件事必须一起读，缺一条就会得出错结论：

1. **`prompt=0` 的行是真噪声，但权重差异极大。** `71458c` 里它只占 2.3%，剔除后 −12.9% → −12.7%，**几乎没动**；`56550a` 里它占 33.9%，一行就决定了判定结果。所以"prompt=0 拉低了整体残差"这句话，对 8 轮的会话成立，对 277 轮的会话**不成立**——后者的差额来自别处。
2. **单轮超长输出确实是大头（`98dc66` 占 41.9%）。** 一轮 30,905 tok，实测 156.6 s vs 预测 125.2 s：多出的 31 s 是服务端在 3 万 token 生成上的排队/限流，而 `α_O` 是单价，不是排队模型。但剔除它只到 −12.5%，**仍不通过**。
3. **剩下的是每步几百毫秒的系统性低估。** `71458c` 剔除噪声后仍有 −171 s、平均 **−631 ms/步**（中位 −232 ms/步），这是 τ0/α 在当天服务端负载下的漂移，也就是"已知局限"里写的工具执行与 retry 未建模。

**判定只认总时间残差，而且只对长跑会话有意义：**

| 会话时长 | n | 残差中位 | \|残差\| < 10% |
|---|---|---|---|
| ≥ 1.5 h | 7 | 3.7% | 6/7 |
| 0.5–1.5 h | 5 | 5.3% | 4/5 |
| 5–30 min | 18 | 9.9% | 10/18 |
| < 5 min | 345 | 11.4% | 164/345 |

> ≥1.5 h 那一格的 MAPE 是 16.7%，被一份 **52 calls / 3.62 h、残差 −98.2%** 的挂起会话拉高；中位数 3.7% 才代表稳态。这类会话要人工剔除，不能计进模型误差。

同理，`71458c` 的 `avg prompt 159,695 tok`、`cache 99.0%`（44.2 M tok / 277 calls）是**观测值**，说明上下文被压得平稳；但它不是收益，收益口径仍然只有 ④。

**我们不会做的事**：把这些行从统计里删掉，再报一个漂亮的 8%。剔除最多把 −14.9% 变成 −12.5%，**过不了就是过不了**。ThriftFlow 拒绝伪造完美残差——上一版 README 报的 −78.7% 已经因为实验设计破裂而整段作废（见 ③），同一个错误不犯第二次。

### ③ 为什么我们**不提供** after-apply 实测

**决定：不做基于单次会话的实测汇报。** 两个理由：

1. **n=1 在统计上没有意义。** 单次会话的任务构成、工具分布、重试风暴都不可控，拿它算误差只是噪声。
2. **宿主配置不受本项目控制。** 本仓库在自己的机器上就踩过一次：
   apply 于 `10-26 22:56` 成功写入，但 **dsh 随即起不来**，用户只好手动把 `cordis.patch.yml` 清空成 `[]`、删掉 `.agent-presets/thriftflow/`。
   于是 after 组全程跑在默认 `0.8W` 下——峰值 177,913（阈值的 2.7 倍）、压缩 0 次，与"阈值生效"完全矛盾。
   那一版 README 报出的 `−78.7% / −41.0%` 因此**全部作废**：那是任务差异，不是收益。

**崩溃根因（已定位并修复）**：`apply` 原先**先写宿主 patch**（把 `default` 改成 `thriftflow`）、**后建 preset 目录**。
而 web profile 是 `patchReload: live`——配置一落盘就热重载，此刻 `thriftflow` 还不存在，于是
`presets: preset "thriftflow" not found`。现在顺序反过来：**preset 组合与元数据先写完，宿主 patch 最后写**，
并在写入前做形状自检、写宿主 patch 前断言 preset 已落盘。

**护栏**：`compare --after-apply` 先校验 `applied.json` 的取值是否还在磁盘配置里，不在就 `exit 2` 拒绝报数（输出见下）。
**回滚**：`apply --uninstall` 纯终端可用，不依赖 dsh 起来——直接剥掉标记块、删 preset 目录、删生效记录。
`down` 掉的 dsh 也能靠这条命令救回来。

```bash
# 1. 审计：时间/token 花在哪
#    带 fixture = 合成日志，clone 下来即可跑；不带参数 = 本机最大的 3 个真实会话
node thriftflow.ts audit test/fixtures/synthetic-long-session.jsonl
node thriftflow.ts audit

# 2. 处方：最优配置 Diff + [ESTIMATED] 投影 + 可粘贴 patch
node thriftflow.ts prescribe                  # 默认对最大的真实会话开方
node thriftflow.ts prescribe test/fixtures/synthetic-long-session.jsonl

# 3. 受控 A/B：同一份日志，只换策略（推荐用这个口径对外）
node thriftflow.ts compare test/fixtures/synthetic-long-session.jsonl

# 4. 落地：写进 dsh 配置（先 --dry-run 看要改哪三处）
node thriftflow.ts apply --dry-run
node thriftflow.ts apply --from=<your-session.zstd>

# 4b. 出事就卸载：纯终端，dsh 起不来也能用
node thriftflow.ts apply --uninstall

# 5. 事后实测：需配置在位 + ≥50 步，否则拒绝报数
node thriftflow.ts compare --after-apply

# 回归自测（需要 ≥2 个真实会话；单份夹具替代不了）
node selftest.ts                              # 25 个最大会话：拟合 + 样本内外残差
node selftest.ts --tables                     # γ / s / ρ 三条曲线
```

> **真实日志不入库**：`$DSH_HOME/sessions/**/*.zstd` 已在 `.gitignore` 里。
> 仓库只带 `test/fixtures/` 下的人工合成夹具——它刻意包含长上下文、缓存未命中、
> 强制压缩、工具截断四类边缘情况，见 [`test/fixtures/README.md`](test/fixtures/README.md)。

`apply` 支持 `--restore=<ts>` 回滚；成功后写 `.thriftflow/applied.json`，作为 `compare --after-apply` 的切分锚点。

## 🛟 `apply` 排雷与安全卸载

`apply` 是本项目唯一**会改写宿主配置**的命令，设计原则是：能不写就不写，写了必须能撤。

### 它到底动哪三处

| 位置 | 改什么 | 为什么必须在这儿 |
|---|---|---|
| `$DSH_HOME/.agent-presets/thriftflow/agent.cordis.yml` | 从内置 `standard` 复制，改写 `compaction-basic` 的 `thresholdRatio` / `retainTokens`、`tool-result-pruner` 的 `thresholdChars` | Web 形态下这两个插件在宿主层被 `disabled: true`，只有 preset 里的实例会生效 |
| `$DSH_HOME/.agent-presets/thriftflow/preset.yml` | preset 元数据（名称 / 描述 / order） | 缺它 preset 列表认不出这个 id |
| `$DSH_HOME/profiles/<profile>/cordis.patch.yml` | `# thriftflow:begin/end` 标记块内的 `spill-policy.maxInlineBytes` + `agent-presets.default: thriftflow` | `spill-policy` 是宿主层行 |

副作用文件两份：备份 `.thriftflow/backups/<ts>/`（含 `manifest.json`）、生效记录 `.thriftflow/applied.json`。

### 四条排雷

1. **写入顺序是安全边界，不是代码风格。** web profile 是 `patchReload: live`：宿主 patch 一落盘就热重载并解析 `default: thriftflow`。若 preset 目录此刻还不存在 → `presets: preset "thriftflow" not found` → **dsh 当场起不来**（本项目真踩过，见 ③）。现在的顺序固定为 preset 组合 → preset 元数据 → 宿主 patch，并且在写宿主 patch 前**再断言一次** preset 已落盘。
2. **匹配不到 / 匹配到多处 → 整体中止，一个字节都不写**（fail-closed）。改的是别人内置 preset 的副本，正则命中 0 处或 2 处都说明形态变了；猜着改就是制造事故。
3. **写前 `preflight`，写后 `verify`。** preflight 只抓三类「loader 连开头都读不下去」的形态：顶层不是列表、缩进里混进制表符、`begin/end` 标记不配对；verify 回读磁盘，确认 `maxInlineBytes` / `retainTokens` / `thresholdChars` 真的在位，否则退出码 1 并给出回滚命令。
4. **没有日志也没有显式数值 → 拒绝执行。** 取值若退化成"文档默认值"，必须显式加 `--allow-defaults`，避免把默认值当处方写进生产环境。

### 出事了怎么救：`--uninstall`（不用备份，纯终端）

```bash
node thriftflow.ts apply --uninstall     # 目标态：配置里根本不存在 thriftflow
```

它只做三件事，**不需要 dsh 起来，不依赖任何 UI**：

1. 从宿主 patch 剥掉 `# thriftflow:begin ... end` 整块；**剥完若只剩注释，自动补一个 `[]`** —— 空文件会被 loader 读成 `null`，同样起不来；
2. 删掉 `$DSH_HOME/.agent-presets/thriftflow/`（并递归清理空掉的父目录，空壳会占住 id 让下次 apply 报"已存在"）；
3. 删掉 `.thriftflow/applied.json`，让 `compare --after-apply` **失去锚点而不是拿着脏锚点报数**。

**为什么卸载不走 `--restore`：** 备份存的是"上一次 apply 之前"的现场，而那份现场本身可能已经带着更早一轮的 thriftflow 块——回滚到它只是换了个旧状态，不是安全状态。两者职责不同：

```bash
node thriftflow.ts apply --uninstall                          # 目标：回到"没有 thriftflow"的干净态（故障时用这个）
node thriftflow.ts apply --restore=2026-10-26T22-11-14-443Z    # 目标：只撤销某一次 apply（备份目录名即 ts）
```

> `--uninstall` 故意**不删备份**：留着用于事后取证，需要时手工清 `.thriftflow/backups/`。

### 万一 dsh 已经起不来（手工三步核对）

```text
1) $DSH_HOME/profiles/web/cordis.patch.yml      → 没有 # thriftflow:begin 标记块（有就整块删掉）
2) $DSH_HOME/.agent-presets/thriftflow/         → 目录已不存在
3) $DSH_HOME/.thriftflow/applied.json           → 记录已删除
```

三条都干净，`patchReload: live` 会把 dsh 热重载回"完全没有 thriftflow"的状态。

### 升级 dsh 之后

preset 是从内置 `standard` **复制**出来的，宿主升级后旧副本会落后。**直接重跑 `apply` 即可幂等刷新**（没有 `--refresh` 参数，重跑本身就是刷新：标记块内的内容会被整块替换）。

## ⚠️ 踩坑笔记

- **`patchReload: live` 下，写入顺序就是安全性。** 宿主 patch 一落盘就会热重载并解析 `default: <preset>`。
  如果先改 `default`、后建 preset 目录，热重载会撞上"preset not found"，**dsh 当场起不来**。
  正确顺序：preset 组合 → preset 元数据 → 宿主 patch。`apply` 已按此排序，并在写宿主 patch 前断言 preset 已落盘。
- **`g` 必须是「上下文每步增量」，不是「缓存未命中的 prefill 体积」。** 这是本项目修过的最贵的 bug：
  旧实现用 `median(freshTokens)`，校准会话上给出 **235**，真实值是 **1,273**（差 5.4 倍）。
  fresh 受缓存驱逐影响、且中位数把工具输出那几步的增长整个抹掉。后果是 `θ*` 被低估到 64,993（正确值 111,445），
  压缩周期被高估到 149 步（正确值 64 步）。**凡是拿 fresh 当增长的地方都要审查。**
- **`maxInlineBytes` 不能凭感觉设小。** 取值是 `clamp(盈亏平衡点, 2KB, 8KB)`；盈亏平衡点 = `(τ0 + 一次工具重取耗时) ÷ (α_M + α_L·n_c/2)` × 4 字节。
  它随压缩周期变化：`g` 修正后周期减半，真实会话的平衡点从 4.5KB 升到 9.5KB，取值因此从 4,500 改回 8,000。**低于平衡点就是纯亏。**
- **会话日志是 zstd 多帧拼接。** Node 的 `zstdDecompressSync` 只解第一帧，会得到 1 行「空会话」。必须按 magic `28 B5 2F FD` 切帧（最长会话 10,309 帧）。
- **`γ`（降智惩罚）默认按 1 处理，未标定。** 它只影响 ρ 的余地和总成本，不改变闭式解的形式。`--tables` 默认参数（ρ=30k, s=2000, g=800）下，γ=2 时 θ*→65.5k、每步 8.44 s。
- **常数只对 `deepseek-flash` 家族成立。** 唯一一个 `deepseek-v4-pro` 会话残差 −53.1%，换模型必须重拟合。

## 不做的事

- 不做「统一截断工具输出」的插件：`dsh-spill-policy` 已常开，改阈值即可。
- 不做「循环守卫」：`dsh-repeat-tool-reminder` 已默认启用。
- 不做「动态工具集」：工具 schema 是每个请求的固定前缀，换工具集会击穿 prefix cache（本会话实测命中 99.7%），省下的远小于损失。
- 不做硬性步数上限：重启任务要重新灌入全部上下文，通常更贵。
- **不做「单次会话实测 Benchmark」**：n=1 没有统计意义，且宿主配置不受本项目控制。

## 已知局限

- **判定口径只对长跑会话成立。** 本机 375 个可计分会话里 191 个 |总时间残差| ≥ 10%，其中 345 个是 < 5 min 的短会话（181 个超标）。短会话的差额由单行噪声（`prompt=0` 重试、3 万 token 单轮）与 τ0 漂移主导，既不能证明也不能证伪模型。实测分布：≥1.5 h 中位 3.7%、< 5 min 中位 11.4%。见 ①b。
- 政策级预测 MAPE **13.7%**（未达 10%）：会话起始上下文已很大时会破坏 `steady` 假设。
- `s` 与 `α_M·θ` 未独立标定（`compaction/summary` 事件不带 usage），压缩项预测偏高 +17.5%。
- 工具执行时间约占墙钟 20%，未建模；retry 未建模。喂入实测均值与实测增长后，时间方程仍有 **−11.6%** 残留误差。
- 校准常数是在 `g` 修正前拟合的；本次只改了 `g` 的定义并重算 `θ*`，未重新拟合 `α_*`。
